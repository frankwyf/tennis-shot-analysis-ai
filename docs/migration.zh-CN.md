# 从 Notebook 到工程化代码：迁移讲解

这份文档专门解释本仓库是如何从“一个探索型 notebook”迁移成“适合开源发布和作品集展示的工程项目”的。

## 为什么要迁移

Notebook 非常适合做早期探索，但当项目需要下面这些能力时，就会显得脆弱：

- 可重复执行
- 明确的依赖管理
- 自动化测试
- 清晰的公开文档
- 在 Jupyter 之外复用

所以，这次改造的目标不是否定 notebook，而是把已经稳定下来的逻辑沉淀到工程结构中。

## 迁移前后的核心区别

### 迁移前：notebook 自己管理一切

原始 notebook 同时负责：

- 参数配置
- 合成数据生成
- 可选的视频姿态提取
- 指标计算
- 可视化

这种方式上手快，但所有责任都堆在一个文件里，后续维护、测试、复用都比较吃力。

### 迁移后：包结构按职责拆分

现在的仓库把这些职责拆到了独立模块里：

- `config.py`：运行参数
- `data.py`：数据生成与姿态提取
- `metrics.py`：指标计算
- `pipeline.py`：流程编排
- `visualize.py`：图表绘制
- `cli.py`：命令行入口

这样 notebook 不再是“唯一的执行容器”，而变成“项目能力的一个使用界面”。

## 对照理解：原 notebook 的内容去了哪里

### 1. 参数开关

原来 notebook 里的：

- `USE_MEDIAPIPE_VIDEO`
- `VIDEO_PATH`
- `MIN_VISIBILITY`
- `MAX_FRAMES`

现在统一收拢进 `AnalysisConfig`。

这样做的好处是：

- 默认值集中
- 更适合命令行映射
- 更容易测试
- 更容易解释项目结构

### 2. 合成数据逻辑

原 notebook 中为了公开演示而构造的挥拍轨迹，现在变成了 `generate_synthetic_landmarks()`。

这一步非常关键，因为它保证了：

- 仓库不依赖私有视频
- 演示结果可复现
- 测试可稳定运行

### 3. 真实视频逻辑

原来 notebook 里对 MediaPipe BlazePose 的调用，现在被封装成
`extract_blazepose_landmarks()`，并使用 MediaPipe Tasks 与用户指定的本地
`.task` 模型文件。这样不会自动下载模型权重，也明确了帧时间戳和资源释放流程。

这意味着：

- 可选依赖集中处理
- 视频路径校验集中处理
- notebook 不需要塞太多异常处理细节

### 4. 指标计算逻辑

原本分散在单元格里的速度与旋转代理计算，被抽到 `compute_metrics()`。

其工程价值在于：

- 绘图和计算分离
- 测试更简单
- 后续扩展更多指标时结构更清晰

### 5. 可视化逻辑

绘图被放入 `plot_analysis()`，让“分析”和“展示”成为两个相对独立的步骤。

这对后续扩展很有帮助，比如：

- 无界面环境运行
- 导出图片
- 以后换成 Web 可视化

## 为什么一定要加 CLI

如果作品集项目只能在 notebook 里运行，工程感通常不够强。

加入 CLI 以后，同一套逻辑可以：

- 在命令行直接运行
- 被脚本调用
- 更容易接入自动化流程
- 更容易写进 README 的 Quick Start

现在仓库支持：

```bash
python -m tennis_shot_analysis --no-show
```

以及：

```bash
tennis-shot-demo --no-show
```

这会显著提升项目的“可交付感”。

## 为什么要加测试

Notebook 更偏交互式结果展示，但发布开源项目时，别人会关心“改了代码会不会坏”。

当前测试覆盖了两个最基础也最重要的面：

- synthetic 分析流程是否返回预期字段
- 输入帧数不足时是否按预期报错

这不是为了追求测试数量，而是为了建立最小可信闭环。

## 为什么还要保留原 notebook

保留原 notebook 反而是加分项，因为它能展示你的思考和工程成长过程。

你可以向别人解释：

1. 先用 notebook 快速验证思路。
2. 再把稳定逻辑抽到包结构中。
3. 最后补 CLI、测试、文档和脱敏说明。

这条演进路径比“直接扔出一个最终工程模板”更有说服力。

## 新的 notebooks 目录有什么意义

新增的 `notebooks/package_workflow_demo.ipynb` 和原始 notebook 的最大区别在于：

- 新 notebook 只负责演示如何调用包
- 主要逻辑不再重复写在 notebook 里
- notebook 与 CLI、测试共享同一套底层实现

这就是工程化的关键特征：

“一个能力，多种入口，共享同一份核心实现。”

## 你在面试或分享里可以怎么讲

可以直接用下面这套表达：

1. 原始项目来自一次 notebook 里的姿态分析探索。
2. 为了公开发布，我先做了脱敏，把默认数据切到 synthetic 路径。
3. 然后把配置、数据处理、指标计算、可视化拆成独立模块。
4. 再补 CLI、测试、README、多语文档和 GitHub 模板。
5. 最终项目既保留了学习痕迹，也具备了工程化展示价值。

## 后续还能怎么继续升级

如果你后面还想把这个项目继续做强，可以考虑：

- 增加动作阶段划分（准备、引拍、击球、随挥）
- 增加时间序列平滑
- 增加真实视频样例的结果导出规范
- 增加一个轻量 Web 展示层
- 增加 benchmark 数据清单和评估脚本
